01

The problem: bad data at the door

One register request, three broken fields, and a server that accepts all of them

Every backend follows the same pattern: the frontend sends data, the server uses it, and it ends up in the database. The weak spot is the word uses. Let's build the simplest register API and watch what happens when a user — or a bot — sends garbage.

The API we're building

POST /api/auth/register needs three things from the frontend:

FieldA good valueThe rule
email"aman@gmail.com"Must look like an email address
phone"9876543210"Must be a 10-digit Indian mobile number
password"Sher@2026"At least 8 characters, and not just spaces

The naive version

This is the code most of us write the first time. It works perfectly — for honest users who never make typos.

models/user.model.js
import mongoose from "mongoose";

const userSchema = new mongoose.Schema({
  email: String,
  phone: String,
  password: String,
});

export const User = mongoose.model("User", userSchema);
controllers/auth.controller.js
import bcrypt from "bcryptjs";
import { User } from "../models/user.model.js";

// ❌ No validation anywhere
export async function register(req, res) {
  const { email, phone, password } = req.body;

  const hashedPassword = await bcrypt.hash(password, 10);
  await User.create({ email, phone, password: hashedPassword });

  res.status(201).json({ success: true, message: "User registered" });
}

What this costs you

ProblemWhat actually happens
Dead accountsThe verification email bounces and the OTP SMS fails. The user can never be verified, but the record stays in your database.
Useless securityA password of three spaces is stored. Anyone who types three spaces into the login form gets in.
Wasted server workbcrypt spent ~100 ms of CPU on garbage. A bot sending 1,000 such requests a minute keeps more than a full CPU core busy doing nothing useful.
Wrong status codesIf the password field is missing, bcrypt.hash(undefined, 10) throws Illegal arguments: undefined, number. Express turns that into a 500 — the client's mistake reported as a server crash, with a stack trace in development.
Security holesA field you expect to be a string can arrive as an object: { "$ne": null }. Pass that into User.findOne({ email }) and it matches the first user in the collection instead of failing.
Key concept

Validation means checking that incoming data has the right presence, type and format before your code uses it. The server is the only place you fully control — whatever you let through the door becomes your problem in the database, in your emails and in your logs.

💡

Your React form is not a gate. Anyone can skip it and call the API directly with Postman, curl or the browser console. HTML attributes like required and type="email" only help honest users. Section 03 proves it.

Quick check

A client sends password: " " to our naive server. What does bcrypt do?

bcrypt doesn't judge input. Three spaces is a valid 3-character string, so you get a normal 60-character hash back. Rejecting it is your job, before hashing.

Quick check

The client forgets the password field, and bcrypt.hash(undefined, 10) throws. Whose mistake is it, and what status code should the client get?

The client sent incomplete data, so it deserves a 400 with a clear message. Without validation, the crash becomes a 500 and the client has no idea what to fix.

02

Validation vs verification

Two checks that sound alike but answer different questions

Before we fix our API, let's get the words right. Students — and plenty of working developers — use these two interchangeably. They are not the same step, they don't happen at the same time, and they don't use the same tools.

Key concept

Validation asks: does this data look right? Format, type, length, required. Your code answers it instantly.
Verification asks: is this data true, and does it belong to this person? Your code can't answer that alone — it needs proof from outside, like an OTP or an email link.

The passport analogy

When you apply for a passport online, the form won't accept a 5-digit PIN code or a date of birth like 32/13/2004. That's validation. A few weeks later, a police officer visits your address to confirm you actually live there. That's verification. A form can be perfectly valid and still be false.

Validation vs verification · two different questionsStep 1 / 5
Validation catches bad format123456789 fails the email format check, so the server answers 400 immediately. There is nothing to verify — we never send a code to something that isn't an email.
A valid email passesaman@gmail.com has the right shape, so validation lets it through. But validation can't tell whether this inbox belongs to the person typing it.
Save, but don't trust yetThe account is created with isVerified: false. The data is valid; the owner is unproven.
Verification needs outside proofThe server emails a one-time code (or link) to that inbox. Only the real owner can read it and send it back.
Now it's trustedThe code matches, so the server sets isVerified: true. The email is valid and verified.
⚠️

Always validate before you verify. Sending an OTP to “abcdefghijklm” wastes an SMS you pay for, and an API that sends messages to unchecked input is an open invitation for spammers.

💡

You'll meet a third word: sanitization — cleaning data instead of rejecting it. Turning Aman@Gmail.com into aman@gmail.com is sanitization. express-validator does validation and sanitization in the same chain.

Quick check

A user types rahul@gmail.com, which is a real address — but it's his friend's inbox, not his. Which check can catch this?

The format is perfect, so validation passes. Only sending a code to that inbox (verification) reveals that the person typing it can't access it.

Quick check

In a register flow, which should run first?

Validation is instant and free. Verification costs time and money, so only valid data should ever reach it.

03

“But my schema already validates!”

Why server-side validation is still needed when Mongoose and the database have constraints

This is the question every student asks at this point. Mongoose lets us write rules right inside the schema, so let's upgrade our model:

models/user.model.js
import mongoose from "mongoose";

const userSchema = new mongoose.Schema({
  email: {
    type: String,
    required: true,
    unique: true,
    match: /^[^\s@]+@[^\s@]+\.[^\s@]+$/,
  },
  phone: {
    type: String,
    required: true,
    match: /^[6-9]\d{9}$/,
  },
  password: {
    type: String,
    required: true,
    minlength: 8,
  },
  isVerified: {
    type: Boolean,
    default: false,
  },
});

export const User = mongoose.model("User", userSchema);

Send the bad request again and Mongoose does reject the email and the phone. So why write validation in Express too? Here are six reasons. The first one surprises almost everyone.

Reason 1 — the database never sees the real password

We hash the password before saving it. So the schema's minlength: 8 is checking the hash, not what the user typed.

Reason 1 · the schema checks the hash, not the passwordStep 1 / 5
The user sends three spacesLength 3. Our schema has minlength: 8, so it should reject this… right?
The controller hashes firstbcrypt.hash(" ", 10) runs before User.create(). It has to — we never store plain passwords.
Out comes a 60-character hashEvery bcrypt hash is 60 characters long, whether the password was three spaces or thirty characters.
The schema checks the hashrequired sees a non-empty string ✓. minlength: 8 sees 60 characters ✓. Both rules pass.
Saved. The rule never had a chance.The only code that ever sees the real password is your Express code, before hashing. That is the only place it can be validated.
the actual Mongoose error

phone: Path `phone` is invalid (abcdefghijklm).

// Notice what's missing: no error for password.
💡

The same trap exists for required: true. Mongoose treats " " as a filled string because its length is 3 — whitespace passes required unless you also add trim: true to the schema field.

Reason 2 — schema checks run too late

Mongoose validates only when you call .save() or User.create(). By then, your controller has already done its expensive work.

Reason 2 · fail fast vs fail lateStep 1 / 5
Same bad request, two serversServer A checks input at the door. Server B relies on its Mongoose schema.
Server A is already doneThe validator rejects all three fields in about a millisecond and replies 400. Server B's request is still walking into the controller.
Server B burns CPUbcrypt spends ~100 ms hashing three spaces. Nobody asked whether the input was even valid.
The schema finally runsMongoose rejects the email and the phone — but only now, after the expensive work. The password passed, because the schema saw a 60-character hash.
Late failure, ugly errorUnless you wrote extra error handling, the client gets a 500 or a raw Mongoose message. In a real app, this step could also come after an image upload or a paid API call.

Reasons 3 to 6

Reason 3
Not all input becomes a document

Login bodies, ?page=abc, /users/:id, OTP codes and confirmPassword never pass through a schema validator. Queries don't run validators either: User.findOne({ email }) happily accepts { "$ne": null }.

Reason 4
Schema validation can be skipped

findByIdAndUpdate() and updateOne() skip validators unless you pass { runValidators: true }. And unique: true isn't a validator at all — it's an index. Duplicates fail later with a MongoDB E11000 error.

Reason 5
Database errors are written for developers

Mongoose says Path `email` is invalid (123456789). Your frontend needs { field: "email", message: "Enter a valid email address" }. Move to PostgreSQL tomorrow and the error format changes again — your API's error format shouldn't.

Reason 6
The frontend can be bypassed

HTML required and type="email" run in the user's browser, which the user controls. One terminal command skips all of it — see below.

Terminal — bypassing the frontend
# No browser, no React form, no HTML "required" — just the API
curl -X POST http://localhost:3000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"123456789","phone":"abcdefghijklm","password":"   "}'
Defense in depth

Keep every layer, because each one has a different job. Frontend validation is for the user's convenience. Server validation is the real gate. Database constraints are the last line of defense — against bugs in your own code and against race conditions, like two sign-ups with the same email in the same millisecond.

LayerIts main jobCan a user bypass it?
Frontend (React / HTML)Instant feedback while typingYes — Postman, curl, DevTools
Server validationReject bad input before any work happensNo
Database schema & indexesGuarantee that stored data stays consistentNo — but it only sees what your code sends it
Quick check

The schema has password: { minlength: 8 } and the controller hashes before saving. A user sends " ". What happens?

The schema only ever sees the hash, and every bcrypt hash is 60 characters. Password rules must run in Express, before hashing.

Quick check

Which validation can a user bypass with a single curl command?

Frontend code runs on the user's machine, so they can skip it entirely. Server-side checks run on your machine — every request has to pass through them.

04

Plain validation, by hand

Write the checks yourself first, so you know exactly what a library does for you

Before reaching for a library, let's validate our three fields with plain JavaScript. For every field, the checks happen in the same order:

Presence and type — is it there, and is it a string?
typeof email !== "string" catches missing fields, numbers, arrays and objects like { "$ne": null } in one go.
Clean — trim what's safe to trim
Spaces around an email or phone are typos. Never trim a password: spaces inside it are allowed.
Format — does it match the rule?
A regex for email and phone, a length check for the password.
Respond — collect every error, answer once
One 400 with a list, so the user can fix all fields in a single attempt.
Step 1 — Validate inside the controller

The quickest version: put the checks at the top of the controller and return early if anything is wrong.

controllers/auth.controller.js
import bcrypt from "bcryptjs";
import { User } from "../models/user.model.js";

const EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
const PHONE_REGEX = /^[6-9]\d{9}$/;

export async function register(req, res) {
  const { email, phone, password } = req.body ?? {};
  const errors = [];

  if (typeof email !== "string" || !EMAIL_REGEX.test(email.trim())) {
    errors.push({ field: "email", message: "Enter a valid email address" });
  }

  if (typeof phone !== "string" || !PHONE_REGEX.test(phone.trim())) {
    errors.push({ field: "phone", message: "Enter a valid 10-digit Indian mobile number" });
  }

  if (typeof password !== "string" || password.trim() === "") {
    errors.push({ field: "password", message: "Password cannot be empty or only spaces" });
  } else if (password.length < 8) {
    errors.push({ field: "password", message: "Password must be at least 8 characters" });
  }

  if (errors.length > 0) {
    return res.status(400).json({ success: false, errors });
  }

  // …and only now, the real work
  const hashedPassword = await bcrypt.hash(password, 10);
  await User.create({
    email: email.trim().toLowerCase(),
    phone: phone.trim(),
    password: hashedPassword,
  });

  res.status(201).json({ success: true, message: "User registered" });
}

What's wrong with this approach?

ProblemWhy it hurts
Controller bloatMost of the function is checks. The real work — hash and save — is buried at the bottom.
Copy-pasted rulesLogin needs the email rule too; update-profile needs the phone rule. The copies slowly drift apart.
Hand-written regexEmail addresses are notoriously hard to match with a regex. Ours is simple and misses plenty of edge cases.
Easy to forgetSkip a single typeof check and email.trim() crashes the moment someone sends a number.
No standard error shapeEvery developer on the team invents their own error format, and the frontend has to handle all of them.
Step 2 — Move the checks into a middleware

A middleware runs before the controller. If the data is bad, it responds and the controller never runs. If the data is good, it calls next(). It can also replace req.body with only the clean, known fields.

middlewares/validateRegister.js
const EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
const PHONE_REGEX = /^[6-9]\d{9}$/;

export function validateRegister(req, res, next) {
  const { email, phone, password } = req.body ?? {};
  const errors = [];

  // 1. email: must be a string that looks like an email
  if (typeof email !== "string" || email.trim() === "") {
    errors.push({ field: "email", message: "Email is required" });
  } else if (!EMAIL_REGEX.test(email.trim())) {
    errors.push({ field: "email", message: "Enter a valid email address" });
  }

  // 2. phone: must be a string with a 10-digit Indian mobile number
  if (typeof phone !== "string" || phone.trim() === "") {
    errors.push({ field: "phone", message: "Phone number is required" });
  } else if (!PHONE_REGEX.test(phone.trim())) {
    errors.push({ field: "phone", message: "Enter a valid 10-digit Indian mobile number" });
  }

  // 3. password: never trim it — just reject empty / spaces-only
  if (typeof password !== "string" || password.trim() === "") {
    errors.push({ field: "password", message: "Password cannot be empty or only spaces" });
  } else if (password.length < 8) {
    errors.push({ field: "password", message: "Password must be at least 8 characters" });
  }

  if (errors.length > 0) {
    return res.status(400).json({ success: false, errors });
  }

  // Pass only clean, known fields to the controller
  req.body = {
    email: email.trim().toLowerCase(),
    phone: phone.trim(),
    password,
  };
  next();
}
routes/auth.routes.js
import { Router } from "express";
import { validateRegister } from "../middlewares/validateRegister.js";
import { register } from "../controllers/auth.controller.js";

const router = Router();

// validateRegister runs first. The controller only runs if it calls next().
router.post("/register", validateRegister, register);

export default router;

💡

Why req.body ?? {}? In Express 5, req.body is undefined when a request arrives with no body at all. Destructuring undefined would crash the middleware itself.

➡️

This works, and for a tiny project it's fine. But the rules are still hand-written, and the next route will need its own copy. That's exactly the gap express-validator fills: tested rules from the validator.js library and one consistent error format.

Quick check

Why check typeof email !== "string" before calling email.trim()?

JSON can carry numbers, arrays and objects. (123).trim() throws a TypeError, which would turn a bad request into a 500.

Quick check

What's the biggest downside of writing validation by hand inside every controller?

A few if-statements cost almost nothing at runtime. The real cost is maintenance: duplicated, inconsistent rules and error formats.

05

express-validator

Tested rules as middleware — the same register API, the clean way

express-validator is a set of Express middlewares built on top of validator.js, a long-standing library of string validators and sanitizers (isEmail, isMobilePhone, isStrongPassword, trim and many more). You describe the rules for each field; it runs them and collects the results.

Install
Terminal
npm install express-validator
💡

Examples use ES modules (import). With CommonJS, write const { body, validationResult } = require("express-validator"). Everything else stays the same.

The building blocks

APIUsed inWhat it does
body("email")validator fileStarts a validation chain for req.body.email. Siblings: query(), param(), header(), cookie().
.isEmail()on the chainA validator: records an error if the value fails.
.trim()on the chainA sanitizer: changes the value for the links after it — and for your controller.
.withMessage("…")after a validatorReplaces the default “Invalid value” message of the validator just before it.
.bail()on the chainStops this field's chain if anything before it has failed.
.hide()sensitive fieldsKeeps the field's value out of error objects. Use it for passwords.
validationResult(req)validate middlewareReads every error the chains recorded.
matchedData(req)controllerReturns only the fields you validated, with sanitized values.
The #1 express-validator bug

A chain never sends a response. body("email").isEmail() only writes results onto req. If nothing reads them with validationResult(req), the bad request walks straight into your controller — as if you had no validation at all.

Step 1 — Write the rules
validators/auth.validator.js
import { body } from "express-validator";

export const registerValidator = [
  body("email")
    .exists().withMessage("Email is required").bail()
    .isString().withMessage("Email must be text").bail()
    .trim()
    .notEmpty().withMessage("Email is required").bail()
    .isEmail().withMessage("Enter a valid email address")
    .toLowerCase(),

  body("phone")
    .exists().withMessage("Phone number is required").bail()
    .isString().withMessage("Phone number must be text").bail()
    .trim()
    .notEmpty().withMessage("Phone number is required").bail()
    .isMobilePhone("en-IN").withMessage("Enter a valid 10-digit Indian mobile number"),

  body("password")
    .hide() // never echo the password back in errors
    .exists().withMessage("Password is required").bail()
    .isString().withMessage("Password must be text").bail()
    .custom((value) => value.trim().length > 0)
    .withMessage("Password cannot be empty or only spaces").bail()
    .isLength({ min: 8 }).withMessage("Password must be at least 8 characters"),
];

    Step 2 — One middleware reads every result
    middlewares/validate.middleware.js
    import { validationResult } from "express-validator";

export function validate(req, res, next) {
  const result = validationResult(req);

  if (result.isEmpty()) {
    return next(); // all good → go to the controller
  }

  return res.status(400).json({
    success: false,
    errors: result.array().map((err) => ({
      field: err.path,
      message: err.msg,
    })),
  });
}
    Step 3 — Wire it into the route
    routes/auth.routes.js

    Prefer to reject unknown fields instead of silently dropping them? Wrap your chains in checkExact(registerValidator). It adds an error of type unknown_fields listing role and isVerified.

    Beyond the body: params and query

    The same idea protects route params and query strings, which never go near a Mongoose schema:

    routes/user.routes.js
    import { Router } from "express";
import { param, query } from "express-validator";
import { validate } from "../middlewares/validate.middleware.js";
import { getUser, listUsers } from "../controllers/user.controller.js";

const router = Router();

// GET /api/users/66f1c0a2b4d3e5f601234567
router.get(
  "/:id",
  param("id").isMongoId().withMessage("Invalid user id"),
  validate,
  getUser
);

// GET /api/users?page=2&limit=20
router.get(
  "/",
  query("page").optional().isInt({ min: 1 }).withMessage("page must be a positive number"),
  query("limit").optional().isInt({ min: 1, max: 100 }).withMessage("limit must be between 1 and 100"),
  validate,
  listUsers
);

export default router;
    why isMongoId() matters

    Query values are always strings — ?page=2 gives you "2". After validation, convert them in the controller with Number(req.query.page ?? 1).

    Prefer objects? checkSchema

    validators/auth.schema.js
    import { checkSchema } from "express-validator";

export const registerSchema = checkSchema(
  {
    email: {
      trim: true,
      isEmail: { errorMessage: "Enter a valid email address" },
      toLowerCase: true,
    },
    phone: {

      isMobilePhone: {

    06
    Other options: Zod and Joi
    Schema-first validation — describe the whole object once, validate it anywhere
    

    express-validator attaches rules to request fields. Zod and Joi work differently: you describe the whole
object as a schema, then ask “does this data match?” Neither is tied to Express — you can use them
in any framework, and Zod even runs in the browser, so one schema can guard both your React form and your API.

    Zod

    validators/auth.zod.js
    import * as z from "zod";

export const registerSchema = z.object({
  email: z
    .string("Email is required")
    .trim()
    .toLowerCase()
    .pipe(z.email("Enter a valid email address")),

  phone: z
    .string("Phone number is required")
    .trim()
    .regex(/^[6-9]\d{9}$/, "Enter a valid 10-digit Indian mobile number"),

  password: z
    .string("Password is required")
    .refine((value) => value.trim().length > 0, {
      error: "Password cannot be empty or only spaces",
      abort: true, // stop here, skip the length check
    })
    .min(8, "Password must be at least 8 characters"),
});
    

    middlewares/validateBody.js
    export const validateBody = (schema) => (req, res, next) => {
  const result = schema.safeParse(req.body);

  if (!result.success) {
    return res.status(400).json({
      success: false,
      errors: result.error.issues.map((issue) => ({
        field: issue.path.join("."),
        message: issue.message,
      })),
    });
  }

  req.body = result.data; // only known, cleaned fields
  next();
};
    

    routes/auth.routes.js
    import { Router } from "express";
import { registerSchema } from "../validators/auth.zod.js";
import { validateBody } from "../middlewares/validateBody.js";
import { register } from "../controllers/auth.controller.js";

const router = Router();

router.post("/register", validateBody(registerSchema), register);

export default router;
    

    safeParse() never throws. It returns { success: true, data } or { success: false, error }, and
error.issues holds one entry per problem, each with a path and a message. Because the middleware
replaces req.body with the parsed data, the slim controller from section 04 works unchanged.
    

    💡
    Why .pipe()? It feeds the trimmed, lowercased string into the email check, so "  Aman@Gmail.com " passes as "aman@gmail.com". And z.object() strips unknown keys by default, so role: "admin" never reaches result.data. Use z.strictObject() to reject unknown keys instead.
    

    🧩
    With TypeScript, z.infer<typeof registerSchema> gives you the type of the clean body for free — no separate interface to keep in sync.

    middlewares/validateBody.js
    export const validateBody = (schema) => (req, res, next) => {
  const { error, value } = schema.validate(req.body, {
    abortEarly: false, // collect every error, not just the first
    stripUnknown: true, // drop fields that aren't in the schema
  });

  if (error) {
    return res.status(400).json({
      success: false,
      errors: error.details.map((detail) => ({
        field: detail.path.join("."),
        message: detail.message,
      })),
    });
  }

  req.body = value; // only known, cleaned fields
  next();
};

    Key concept
    All three solve the same problem. The pattern is what matters: validate at the gate, answer 400 with field-wise errors, and pass only clean, known fields to the controller. Once you understand that, switching libraries is a one-afternoon job.
    


    Quick check
    In Zod, what does safeParse() do when the data is invalid?
    parse() throws; safeParse() returns a result object. That's why the middleware can simply check result.success.
    


    Quick check
    Joi stops at the first error by default. Which option collects every error?
    abortEarly defaults to true in Joi. Set it to false so users can fix all their fields in one go.
    

    

    07
    The full picture
    Where validation, business rules and verification sit in a real register flow
    

    Let's put everything together. Validation is the first server-side step, but it isn't the only one.
    

    The full register flowStep 1 / 6
    The form submitsFrontend validation already helped the user fix typos. The server still treats every byte as untrusted.
    Validation — the gatePresence, type, format and allowed fields. Anything wrong → 400, and nothing after this step runs.
    Business rulesValid data can still be unacceptable: this email may already be registered → 409 Conflict. These checks need the database, so they come after validation.
    Save the userHash the password and create the user with isVerified: false. The unique index on email is the last safety net.
    VerificationSend a one-time code or link. This is the only step that proves the email or phone belongs to this person.
    TrustedOnce the code matches, set isVerified: true. The data is now valid, acceptable and verified.
    


    controllers/auth.controller.js — the complete version
    import bcrypt from "bcryptjs";
import { matchedData } from "express-validator";
import { User } from "../models/user.model.js";
import { sendVerificationEmail } from "../services/email.service.js";

export async function register(req, res) {
  // 1. Validation already passed (registerValidator + validate)
  const { email, phone, password } = matchedData(req);

  // 2. Business rule: valid data can still be unacceptable
  const alreadyRegistered = await User.exists({ email });
  if (alreadyRegistered) {
    return res.status(409).json({ success: false, message: "Email already registered" });
  }

  // 3. Save — isVerified defaults to false in the schema
  const hashedPassword = await bcrypt.hash(password, 10);
  const user = await User.create({ email, phone, password: hashedPassword });

  // 4. Verification starts here: send a link / OTP to the email
  await sendVerificationEmail(user);

  res.status(201).json({
    success: true,
    message: "Account created. Check your inbox to verify your email.",
  });
}
    


    💡
    You can also move the “already registered” check into the chain as an async custom validator. It will then come back as a 400 through validate instead of a 409:
    

    validators/auth.validator.js — optional
    body("email")
  // ...the format rules from section 05...
  .bail() // never query the database for "123456789"
  .custom(async (email) => {
    const exists = await User.exists({ email });
    if (exists) throw new Error("Email already registered");
  }),
    


    ⚠️
    Keep the unique index anyway. Two sign-ups with the same email can pass User.exists() in the same millisecond. Only the database index stops the second one — and it fails with MongoDB error code 11000, which you should turn into a 409:
    

    controllers/auth.controller.js — handling the race
    const hashedPassword = await bcrypt.hash(password, 10);

try {
  await User.create({ email, phone, password: hashedPassword });
} catch (err) {
  if (err.code === 11000) {
    // duplicate key: someone registered this email a moment ago
    return res.status(409).json({ success: false, message: "Email already registered" });
  }
  throw err; // anything else is a real server error
}

    Common mistakes
    

    MistakeThe fix
    Validating only in ReactAlways validate on the server. Frontend checks are for convenience.
    Forgetting validationResult(req)Chains only record errors. Always add the validate middleware after them.
    notEmpty() without trim()"   " has length 3 and passes. Trim emails and phones first; use a custom check for passwords.
    Trimming passwordsDon't. Spaces are legal password characters. Reject whitespace-only passwords instead.
    User.create(req.body)Use matchedData(req), or the parsed value from Zod / Joi.
    Sending raw error arraysMap them to { field, message } and add .hide() on sensitive fields.
    Treating unique: true as validationIt's an index. Catch error code 11000 and return 409.
    Sending an OTP before validatingValidate first. SMS messages cost money, and unchecked input invites spam.
    


    The one-paragraph summary
    Validation checks that data looks right. Business rules check that valid data is acceptable. Verification proves the data is real and belongs to the user. Database constraints catch whatever slips past your own code. A production API needs all four — and validation always comes first, because it's the cheapest.
    


    Quick check
    Where should isVerified: true come from?
    If the client could set it, verification would mean nothing. matchedData(req) (or Zod/Joi stripping) keeps it out of the register request.
    


    Quick check
    An email passes validation and the “already registered” check, but two identical sign-ups arrive in the same millisecond. What finally stops the duplicate?
    Both requests can run the existence check before either one saves. Only the database index guarantees uniqueness — that's why you keep it even with server-side checks.
